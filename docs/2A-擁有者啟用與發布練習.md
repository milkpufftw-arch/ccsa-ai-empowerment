# 擁有者啟用編輯與第一次發布練習

目前只有一位管理員時，可選擇「只有試算表擁有者可以寫入」。Google 登入、啟用中的 AdminUsers 白名單、試算表編輯權限及操作者／執行者一致檢查都會保留；其他白名單帳號也不能新增、編輯、刪除、下架或下載公開資料檔。多人管理仍須另做跨帳號驗收。

**「擁有者可寫入」是編輯資格；Google 網頁部署仍須「以存取者身分執行」。** 不要把執行身分改成「我」。

## 第一步：在 Google 套用程式

先保留指令碼屬性 `WRITE_ENABLED=false`。建議以本版本完整 `apps-script/Server.gs` 取代 Google 專案中原有的同名檔案，避免局部貼入時多留大括號。熟悉程式的維護人員也可只替換 `writesEnabled_(ctx)`，原有不傳參數的呼叫亦相容。程式替換不會清除試算表內容。

儲存後，選「部署 → 管理部署」，找到目前使用的網頁應用程式，按鉛筆編輯，版本選「新版本」。確認實際設定是：

| Google 部署設定 | 必須符合 |
| --- | --- |
| 執行身分 | 存取網頁應用程式的使用者（USER_ACCESSING） |
| 誰可以存取 | 需要登入 Google 的使用者（ANYONE，不含匿名） |

確認後更新**既有部署**，保留原 `/exec` 網址。這次更新不用重新初始化試算表；初始化會再次關閉寫入。

## 第二步：開啟本人寫入

在「專案設定 → 指令碼屬性」設定下列值。後兩項是維護者核對上表實際設定後留下的確認值，不是程式向 Google 自動取得的設定；必須據實填寫。

| 屬性 | 值 |
| --- | --- |
| ADMIN_WRITE_MODE | owner_only |
| DEPLOYMENT_EXECUTE_AS | USER_ACCESSING |
| DEPLOYMENT_ACCESS | ANYONE |
| WRITE_ENABLED | true |

保留既有 `SPREADSHEET_ID`。此模式不用填寫或修改 `SECURITY_REVIEW_JSON`，也不把第二帳號測試記為通過。

儲存後重新整理原管理後台 `/exec`。使用試算表擁有者自己的 Google 帳號，唯讀提示應消失，「新增」按鈕應可使用。如果仍唯讀，確認登入帳號、AdminUsers 啟用狀態、擁有者身分、四個屬性及目前 `/exec` 是否已更新到新版本。不要改用前端傳入 Email 或開放匿名存取。

## 第三步：先練習一則公告

1. 左側「公告 → 新增公告」。
2. 標題填「網站發布流程練習」，分類選「最新消息」。
3. 摘要及內容填寫完全虛構、可公開的練習文字，選擇公告日期。
4. 發布狀態先選「草稿」，按「儲存」。回到清單確認存在，再開啟「編輯」，確認是同一筆資料。
5. 用「預覽公開欄位」核對內容。確認後將發布狀態改為「已發布」，再儲存。

這時資料已在內部 Google Sheets，尚未更新民眾看到的網站。練習公告可先留在前台預覽環境確認；只有確定要公開的內容才合併發布。

## 第四步：下載公開資料檔

1. 左側「公開資料發布 → 預覽已發布 JSON」。確認有剛才的公告，且自由文字內容均可公開。
2. 按「下載公開 JSON」，取得 `content.json`。若瀏覽器將重複下載的檔案改名成 `content (1).json`，先確認它是最新檔案，再將名稱改回 `content.json`。
3. 只使用這份後台匯出的公開檔案。不要上傳整份試算表、AdminUsers、AuditLogs、內部備註或備份。可將公開檔案另存至受限 Drive 資料夾，供交接及備份。

## 第五步：透過 GitHub 更新前台，不用終端機

完成第一次發布後，日常請使用 [日常更新逐步教學](./2A-日常更新逐步教學.md)，從 main 建立新的內容更新分支；該手冊逐項列出畫面按鈕、完成檢查及常見問題。

第一次更新可開啟 [本次更新分支的 public/data 資料夾](https://github.com/milkpufftw-arch/ccsa-ai-empowerment/tree/codex/owner-only-admin-writes/public/data)，將公開 `content.json` 上傳並直接提交到該分支，再從該分支建立 PR；這會將擁有者模式、部署前資料檢查及這一批公開資料一起納入同一個可審閱更新。合併後，後續日常更新依下列 main 分支流程操作。

1. 用自己的 GitHub 帳號開啟 [專案 public/data 資料夾](https://github.com/milkpufftw-arch/ccsa-ai-empowerment/tree/main/public/data)。
2. 按「Add file → Upload files」，選剛才的 `content.json`，目標是取代 `public/data/content.json`。
3. 提交說明可寫「更新計畫公開資料」。選擇建立新分支並提出 Pull request，再按「Propose changes／Commit changes」及「Create pull request」（實際按鈕依 GitHub 畫面為準）。
4. 在 PR 的 Vercel Bot 留言開啟 **Preview 連結**，不要點留言輸入框的 Preview。
5. 在預覽首頁「計畫新鮮事」確認公告，點開確認內容。公告日期較新的資料會排前面，首頁最多顯示五則。
6. 確定要對外公開後，按「Merge pull request → Confirm merge」。等待 Vercel 新的 Production 部署 Ready，再重新整理 [正式前台](https://ccsa-ai-empowerment.vercel.app/)。

新版建置會先執行公開資料契約檢查；JSON 無效或夾帶額外欄位時會中止建置。這能避免錯誤資料更新正式網站，不能取代上傳 GitHub **之前**的個資與公開授權人工檢查。

若需要由維護人員協助，可交付已人工確認的公開 `content.json`，由維護人員執行 `npm run content:import -- /路徑/content.json`、檢查差異及部署。不要交付內部試算表或憑證。

## 各種資料會出現在哪裡

| 後台資料 | 前台位置 |
| --- | --- |
| 合作機構 | `/seed` 的合作機構清單及機構詳細頁 |
| 課程活動 | `/courses` 清單及課程詳細頁 |
| 公告 | 首頁「計畫新鮮事」及公告詳細頁 |
| 招募設定 | `/seed` 的申請說明與 Google Forms 申請按鈕；需同時符合開放狀態與招募日期 |

儲存代表內部記錄已更新；「已發布」代表會進入下一次匯出；合併公開資料更新並完成 Vercel 部署後，民眾才會看到。下架、刪除及報名狀態變更亦須重新匯出及部署。

需要暫停時，將 `WRITE_ENABLED` 改回 `false` 並儲存，下一次操作即會被拒絕。僅刪除 `SECURITY_REVIEW_JSON` 不會停用 owner_only 模式。未來多人編輯可改回 `ADMIN_WRITE_MODE=reviewed_admins`，並依安全部署文件完成真實跨帳號驗收後啟用。
